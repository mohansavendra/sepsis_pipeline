# Take-Home Assignment: Extracting and Checking Sepsis Criteria with an LLM

## 1. Overview

This project evaluates the use of Large Language Models (LLMs) and rule-based validation to answer clinical abstraction questions related to the CMS SEP-1 sepsis measure.

The dataset contains 100 synthetic clinical encounter records generated using Synthea. Each record includes a clinical question, a clinical context, and an answer generated by another AI model.

The primary objectives are to:

- Answer clinical abstraction questions using the available clinical context.
- Provide evidence supporting every prediction, including relevant values and timestamps.
- Identify incorrect, unsupported, hallucinated, or incomplete answers from another AI model.
- Evaluate performance using labeled development data.
- Design a production-ready workflow with appropriate privacy controls and human oversight.

## 2. AI-Assisted Development

AI tools may be used throughout the assignment to assist with:

- Designing the pipeline architecture and implementation approach.

All generated code and outputs should be tested and validated. The implementation should be understandable, reproducible, and explainable during the technical interview.

## 3. Dataset

The project uses the following input files.

Contains 100 records, with 20 development records and 80 test records.

Important columns:

| Column | Description |
|---|---|
| `record_id` | Unique identifier for each record |

Contains reference labels for the 20 development records.

- `correct_value`: Reference yes/no answer.
- `model_answer_is_correct`: Indicates whether the other model's answer matches the reference label.

The development labels are used to evaluate and refine the pipeline. The hidden test labels must not be used for tuning.

## 4. Clinical Criteria

The pipeline handles four question families using the definitions provided in the assignment.

### 4.1 SIRS

Determine whether at least two distinct SIRS criteria are met.

| Parameter | Threshold |
|---|---|
| Temperature | Greater than 38.0°C or less than 36.0°C |
| Heart rate | Greater than 90 beats/min |
| Respiratory rate | Greater than 20 breaths/min |
| White blood cell count | Greater than 12 or less than 4 × 10³/µL |

The implementation should identify the relevant measurements, evaluate the thresholds, and document the evidence used to reach its conclusion.

### 4.2 Infection

Determine whether infection is explicitly documented in the clinical context.

Infection must not be inferred solely from symptoms, abnormal laboratory results, or antibiotic use.

### 4.3 Antibiotic

Determine whether an antibiotic was started during the encounter.

The evidence should identify the relevant medication and any available administration or start timestamp. A medication mention alone should not automatically be treated as proof that treatment was started.

### 4.4 Organ Dysfunction

Evaluate the laboratory thresholds specified in the assignment.

| Parameter | Threshold |
|---|---|
| Creatinine | Greater than 2.0 mg/dL |
| Platelets | Less than 100 × 10³/µL |
| Total bilirubin | Greater than 2.0 mg/dL |

The implementation should extract the relevant laboratory values, compare them with the thresholds, and retain the corresponding timestamps where available.

## 5. Implementation Approach

The solution uses a combination of deterministic Python rules and AI-assisted information extraction where appropriate.

### 5.1 Information Extraction

Extract relevant clinical facts from the encounter context, including:

- Vital signs and measurement timestamps.
- Laboratory values and collection timestamps.
- Explicit infection documentation.
- Medication names and available start or administration times.

### 5.2 Rule-Based Evaluation

Apply the specified clinical thresholds and question-specific logic to the extracted information.

Deterministic rules are preferred for numerical threshold comparisons because they are reproducible and straightforward to validate.

### 5.3 Evidence Generation

Every prediction should include supporting evidence derived from the original clinical context.

Evidence should contain the relevant values, timestamps, and documentation needed to understand the decision. The pipeline must not invent measurements, events, medication administrations, or timestamps.

If the available context does not establish an answer reliably, the limitation should be documented rather than concealed.

### 5.4 Model Answer Validation

Independently evaluate the other model's answer against the clinical context and reference criteria.

The validation process should consider both the final yes/no verdict and the evidence used to justify it.

## 6. Error Classification

Each model answer must be classified as acceptable or unacceptable.

For unacceptable answers, use one of the following error categories:

| Error type | Description |
|---|---|
| `wrong_value` | The yes/no verdict is incorrect. |
| `hallucinated_detail` | The explanation cites a detail that is not present in the clinical context. |
| `right_answer_wrong_reason` | The verdict is correct, but the supporting reasoning is unsupported or invalid. |
| `incomplete` | The answer omits necessary evidence or does not adequately address the question. |

For acceptable answers, `model_answer_acceptable` should be `True` and `error_type` should be blank.

The classification should distinguish factual correctness from reasoning quality. A correct verdict alone does not establish that an answer is acceptable.

## 7. Evaluation Strategy

The pipeline is evaluated using the 20 labeled development records.

### 7.1 Development Evaluation

Measure and document:

- Prediction accuracy against `correct_value`.
- Performance by question family where the sample size permits.
- Evidence grounding and traceability.
- Accuracy of the other model's answer-acceptability assessments.
- Distribution of error categories.

Use the development results to identify weaknesses and make targeted improvements.

### 7.2 Failure Analysis

Document at least three failure cases, including:

1. The clinical question and relevant context.
2. The pipeline prediction and supporting evidence.
3. The expected answer or identified error.
4. The reason the failure occurred.
5. The proposed corrective action.

### 7.3 Unseen-Data Performance

Discuss expected performance on unseen records using the development results, the dataset's limitations, and the reliability of the extraction and validation logic.

The 80 test records should be processed using the finalized pipeline without consulting hidden labels for tuning.

Results should distinguish measured development performance from expected test performance. No unmeasured accuracy figures should be reported as actual results.

## 8. Production Deployment: Azure and Microsoft Fabric

A production workflow could run monthly within an appropriately configured Microsoft Azure or Microsoft Fabric environment.

### 8.1 PHI Protection

- Use approved organizational environments and access-controlled services.
- Apply least-privilege access and role-based permissions.
- Encrypt data in transit and at rest.
- Avoid sending identifiable clinical information to unapproved external AI services.
- Minimize sensitive data in application logs and monitoring systems.
- Apply organizational retention, deletion, and auditing policies.

### 8.2 Logging and Traceability

For each processing operation, capture appropriate metadata, including:

- Record identifier or approved pseudonymous identifier.
- Model and prompt versions.
- Pipeline and rule versions.
- Processing timestamp and execution status.
- Extracted evidence and resulting prediction.
- Validation outcome and human-review status.

Sensitive clinical text should not be copied into general-purpose logs unnecessarily. Access to detailed audit records should be restricted and monitored.

### 8.3 Accuracy Monitoring

- Collect reviewed outcomes from clinical abstractors.
- Compare predictions against verified labels over time.
- Track accuracy and error rates by question family.
- Monitor evidence-grounding failures and changes in input formats.
- Investigate performance degradation before promoting pipeline changes.
- Version models, prompts, and rules to support reproducibility.

### 8.4 Human Review

Prioritize human review when:

- Evidence is missing, ambiguous, or contradictory.
- A required timestamp or measurement cannot be established.
- The extracted value is malformed or has an uncertain unit.
- The model's explanation contains unsupported details.
- The answer is near a decision threshold or depends on conflicting measurements.
- The system identifies a high-risk or low-confidence case.

Confidence scores should only be used for review routing after they have been evaluated and calibrated. High-risk decisions should not bypass required human review solely because a model reports high confidence.

```bash
.venv\Scripts\activate
```

```bash

source .venv/bin/activate
```

If using a hosted LLM, configure the required API credentials through environment variables. Do not hardcode API keys in the source code or commit them to version control.

If LLM access is unavailable, the project should provide a deterministic stub or fallback so the pipeline can execute end to end.

2. Process each clinical question.
3. Generate predictions and evidence.
4. Assess the other model's answers.

The exact command should match the final script or entry point included in the repository.

## 11. Limitations

This project uses synthetic data and is intended for technical evaluation, not direct clinical decision-making.

Performance on synthetic records does not establish clinical validity or demonstrate readiness for real patient deployment. Clinical definitions, source-data quality, extraction reliability, and review requirements must be validated before any real-world use.

The solution prioritizes evidence-grounded answers, transparent error classification, reproducibility, and human oversight over unsupported claims of accuracy.
